# Compliance — Owner Console (ITCHATHON)

Practical obligations per module and the control that meets each one. Code references: `app/platform/redact.js`, `guard.js`, `retention.js`, `audit.js`, `auth.js`, `ratelimit.js`; prompt clause `prompts/meta/compliance_clause.md`. Where a threshold varies by jurisdiction it says "varies; check" — do not fill in a number from memory.

## 1. Returns root-cause (buyer reviews, messages, return comments)
- **Roles.** The seller is the controller of buyer data; we are a processor acting on their instruction (GDPR Art. 28 / UK GDPR; CCPA "service provider"). A Data Processing Agreement with every seller is required before production use, covering sub-processors (the model provider) and the deletion/return-of-data duty at contract end.
- **Lawful basis** (seller's, documented in their records): legitimate interest (Art. 6(1)(f)) in reducing returns; buyers reasonably expect their return comments to be read by the seller. We rely on the seller's basis, not our own. CCPA: seller must not "sell" or "share" this data; our contract says we use it only to produce the read.
- **Amazon Seller Central Data Protection Policy** (applies because inputs originate from Seller Central / SP-API): no retention of PII beyond 30 days after order fulfilment except as needed for tax/compliance; buyer data used only for the purpose it was received (order handling, not marketing/enrichment); encryption at rest and in transit; access logging. Our answer: `redact()` strips PII *before* any storage or model call, so what we hold is (a) a SHA-256 hash of the raw input for dedupe/audit and (b) redacted text; `retention.js` deletes raw imports at 30 days. Amazon also forbids sharing PII with third parties not needed for the order — the model provider therefore only ever sees placeholders.
- **Etsy API Terms of Use**: use Etsy data only for the member's own shop, no aggregation across shops, delete on member request, no display of buyer personal data outside what Etsy exposes. Same redaction + per-tenant isolation (`auth.js`) covers this. Etsy requires disclosure that the app is not endorsed by Etsy — keep it in the UI footer.
- **What we store:** `{tenant_id, sha256(raw_input), redacted_input, prompt_version, model_output, guard_issues, ts}` in `data/audit/*.jsonl`; raw uploads in `data/raw_imports/` (30 days); nothing else. The redaction `map` (placeholder → original) is returned to the request and **never written** to disk.
- **DSAR path:** buyers ask the *seller*; the seller asks us with the order id or a text fragment; we grep the audit log for the tenant, return matching redacted lines, and delete on request (`retention.js` accepts a one-off cutoff). Target: answer to seller within 7 days so the seller can meet their 30-day (GDPR) / 45-day (CCPA) window.
- **Retention:** audit 90 days, raw imports 30 days (defaults in `retention.js`); run daily from cron; `--dry-run` output is kept as evidence the sweep ran.

## 2. Ads account plain-read (Google Ads / Meta Marketing API)
- **Google Ads API Terms + Required Minimum Functionality / Meta Platform Terms & Marketing API policy:** data pulled for one advertiser is used only to serve that advertiser; **no pooling or benchmarking across clients** (Google explicitly prohibits combining data across customers without consent; Meta prohibits using Platform Data to build or augment profiles). Our module reads one account, writes one plain-English read, stores nothing but the audit hash. No cross-tenant tables exist by design.
- Tokens: OAuth refresh tokens stored encrypted, scoped read-only, revoked on tenant deletion; the Google API Services User Data Policy "limited use" rule applies if Google user data is touched.
- **Account ownership guidance is not legal advice.** When the module explains who "owns" an ad account vs an agency, the output must be phrased as how the platform's admin roles work, with a pointer to the platform's own help pages. The compliance clause forbids legal advice; the guard rejects URLs so the UI, not the model, links to Google/Meta help.
- **Ad-claim substantiation.** FTC Deceptive Advertising standards (and the UK ASA / CAP Code) require a reasonable basis for objective claims. If the plain-read says variant B "won", that is a claim the owner may reuse in marketing. This is why the module has a **statistics floor**: it may only say "won/better" when the sample and the test meet the floor defined in the module; below it, it says "not enough data to call a winner". The eval enforces this the same way it enforces `not_enough_data` for returns.

## 3. In-store theft deterrence (camera alert → de-escalation script)
- **Scope is narrow by design:** the module receives a text alert from the camera vendor (zone, time, optional free-text `person_description`) and returns a non-confrontation script for staff. It never receives video frames or images. **No facial recognition, no biometric identification, no re-identification** — this keeps us out of Illinois BIPA (and Texas/Washington biometric laws), GDPR Art. 9 special-category processing, and the EU AI Act's prohibited/high-risk categories for biometric identification in public spaces (untargeted scraping and real-time remote biometric ID are prohibited; post-hoc biometric ID is high-risk). Do not add it later without a full DPIA and legal review.
- **Signage and lawful basis for the camera** are the store's responsibility, not ours, but the onboarding checklist must ask: UK — ICO CCTV/video-surveillance guidance under UK GDPR/DPA 2018 (signage, DPIA if systematic monitoring, retention proportional); EU — national DPA rules on video surveillance, EDPB Guidelines 3/2019; US — state law varies; if the camera records **audio**, two-party/all-party consent states (e.g. California, Florida, Washington and others — varies; check) may require notice or consent.
- **Clip retention belongs to the camera vendor.** We keep only the alert record (`data/theft/*.jsonl`, 365 days for incident history). `person_description` is free text that could identify someone or encode protected characteristics; `retention.js` blanks it to `[REDACTED]` after 24 hours. Staff must never enter race, ethnicity, religion, or similar in it; the UI placeholder text says "clothing and location only".
- **Anti-discrimination.** The playbook never conditions on protected characteristics; the prompt is given zone/time/behaviour only. The compliance clause plus `guard.js` (`pii_in_output`) prevents the model echoing identifying details back.
- **Non-confrontation = employee safety.** Scripts are limited to customer-service approaches ("Can I help you find anything?"), calling a manager, or noting time/zone for police. This follows OSHA's workplace-violence guidance for late-night retail (avoid confrontation, no pursuit) and most retailers' insurance conditions. The script must never instruct staff to detain, touch, block, follow outside, or accuse anyone.

## 4. Kitchen prep forecasting (POS data)
- POS sales lines by item/hour are not personal data once tender/loyalty ids are dropped; the importer keeps only `{item, qty, ts, price}`. If a POS export contains card numbers or names, `redact()` runs on import and the raw file is deleted at 30 days.
- Weather providers (e.g. Open-Meteo, OpenWeather) have attribution and rate-limit terms and forbid redistribution of raw data — cache per tenant, show attribution in the UI, and do not expose the raw feed.
- Forecasts are decision support, not instructions; the output says "suggested prep" and shows the sample size it was built from.

## 5. Cross-cutting
- **EU AI Act transparency (limited-risk):** every read shows "Produced by an AI system; check before acting" and the audit log records `prompt_version` and model id so any output can be reproduced. None of the four modules falls into an Annex III high-risk category as scoped; the theft module stays out only because it does no biometric or emotion recognition.
- **Model provider:** Anthropic Usage Policy applies (no biometric ID, no harassment, no deceptive content). Use commercial API terms; Anthropic's commercial terms do not train on API inputs/outputs by default; a zero-data-retention arrangement is available for enterprises and should be requested before processing EU buyer text at scale. Inputs are redacted regardless.
- **Prompt injection:** buyer text is untrusted. It is wrapped in `<untrusted_buyer_text>` by `wrapUntrusted()`, the compliance clause tells the model to treat it as data, `injectionScore()` logs suspicious inputs (not blocked — an angry review may say "ignore"), and `checkOutput()` rejects outputs whose evidence is not verbatim, that contain URLs, off-marketplace contact advice, or leaked prompt text.
- **Secrets:** `.env` is git-ignored and never committed; API keys live only in the server process; rotate on any suspected exposure and at least every 90 days; no keys in the browser bundle.
- **Audit log integrity:** append-only JSONL per tenant with hashed inputs; each line carries the previous line's hash so tampering is detectable (implemented in `audit.js`); the retention sweep is the only writer that rewrites files, and it logs what it removed.
- **Access control:** every request is scoped to a `tenant_id` from `auth.js`; storage paths and audit files are keyed by tenant; no endpoint takes a tenant id from the body.
- **Incident response:** personal-data breach → notify the affected seller (controller) without undue delay so they can meet GDPR Art. 33's 72-hour deadline to the supervisory authority; record every incident in `docs/incidents/`, even those judged not notifiable. US state breach-notification deadlines vary; check per state.
- **SOC 2 mapping (Common Criteria):** CC6.1 logical access → `auth.js`; CC6.6/CC6.7 boundary protection and transmission → HTTPS + `ratelimit.js`; CC7.2 monitoring → `audit.js` + injection logging; CC6.5 disposal → `retention.js`; CC8.1 change management → eval gates below; CC9.2 vendor management → DPA + Anthropic/Google/Meta terms review.
- **Accessibility:** UI targets WCAG 2.1 AA (contrast ≥ 4.5:1, keyboard-operable, labels on every input, no information by colour alone). Required in the EU from June 2025 for many e-commerce services under the European Accessibility Act; check applicability.
- **Eval gates as release controls.** A prompt version ships only when `evals/run.py` passes: cause accuracy ≥ 0.80, grounded rate ≥ 0.95, low-data honesty ≥ 0.99. The grounded gate is also the PII gate — because redaction runs before the model call and before the check, a prompt that quotes anything not in the redacted input fails. The generated prompt must contain the compliance clause verbatim (`generate.py` appends it if the model dropped it). Failing any gate blocks the release; the result JSON is the evidence for the change-management record.
